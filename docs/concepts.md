# מושגי יסוד – הכלים של הפרויקט

הסבר על כל כלי: מה הוא, איך הוא עובד, ומה כדאי לדעת לראיון.
כשאפשר, יש השוואה לעולם של ג'אווה.

---

## Node.js

### מה זה
השפה JavaScript נולדה כדי לרוץ רק בתוך הדפדפן. **הכלי Node.js** הוא תוכנה שמריצה JavaScript מחוץ לדפדפן, ישירות על המחשב או על שרת.
בפנים הוא משתמש ב־V8, מנוע ה־JavaScript של כרום, ומוסיף לו את מה שאין לדפדפן: גישה לקבצים, לרשת, לתהליכים.

### ההשוואה לג'אווה
| ג'אווה | העולם של Node |
|---|---|
| JVM – מריץ bytecode | Node.js – מריץ JavaScript |
| הפקודה `javac` מקמפלת | הכלי `tsc` (או Next.js) מתרגם TypeScript ל־JavaScript |
| Maven / Gradle | npm |
| הקובץ `pom.xml` | הקובץ `package.json` |
| ספריות ב־`~/.m2` | ספריות בתיקייה `node_modules` של הפרויקט |

### איך הוא עובד: לולאת האירועים (event loop)
זה הרעיון הכי חשוב, והוא נשאל הרבה בראיונות.
- בג'אווה קלאסית, שרת מטפל בכל בקשה ב־thread נפרד. כשבקשה מחכה למסד הנתונים, ה־thread שלה "תקוע" ומחכה.
- בתוך Node יש **thread ראשי אחד** שמריץ את הקוד שלך. כשהקוד מבקש משהו איטי (קריאה מהרשת, מהדיסק), הבקשה נמסרת למערכת ההפעלה, וה־thread ממשיך לטפל בדברים אחרים. כשהתשובה מגיעה, פונקציית ההמשך שלך נכנסת לתור ורצה.
- בקוד זה נראה כך: `await fetch(...)`. המילה `await` לא חוסמת את התוכנית כולה, אלא רק "משהה" את הפונקציה הזאת עד שהתשובה תגיע.

**המשמעות**: התכנון הזה מצוין לשרתים שרוב הזמן מחכים לרשת ולמסד הנתונים (כמו האתר שלנו), וגרוע לחישובים כבדים, כי חישוב ארוך תוקע את ה־thread היחיד.

### למה צריך אותו אצלנו
הכלי Next.js עצמו הוא תוכנה שכתובה ל־Node. בזמן פיתוח הוא מריץ את שרת הפיתוח, ובפריסה, Vercel מריץ את הקוד שלנו על Node.

### שאלות ראיון
- "מה ההבדל בין Node לבין JavaScript?" – הראשון הוא סביבת הרצה, השני הוא שפה.
- "האם Node הוא single-threaded?" – הקוד שלך רץ על thread אחד, אבל קלט/פלט מתבצע ברקע, בעזרת מערכת ההפעלה ומאגר threads פנימי.
- "מה זה `package-lock.json`?" – הקובץ נועל את הגרסאות המדויקות של כל הספריות (כולל ספריות של ספריות), כדי שכל מי שמתקין יקבל בדיוק את אותו הדבר.

## Docker

### הבעיה שהוא פותר
"אצלי זה עובד." תוכנה תלויה בסביבה: גרסת מערכת ההפעלה, ספריות מותקנות, הגדרות. כשמעבירים אותה למחשב אחר, משהו שונה והיא נשברת.

### מה זה
הכלי Docker אורז תוכנה **יחד עם כל הסביבה שהיא צריכה** לחבילה אחת, ומריץ אותה בבידוד.
- **אימג' (image)**: התבנית. קובץ קפוא שמכיל מערכת קבצים מינימלית, ספריות והתוכנה עצמה. נבנה מתוך קובץ מתכון שנקרא `Dockerfile`.
- **קונטיינר (container)**: מופע רץ של אימג'.
- **ההשוואה לג'אווה**: אימג' הוא כמו class, וקונטיינר הוא כמו אובייקט. מאותו אימג' אפשר להריץ כמה קונטיינרים.

### איך זה עובד מתחת למכסה
זו הנקודה שרוב המועמדים מפספסים: **קונטיינר הוא לא מכונה וירטואלית.**
- מכונה וירטואלית מדמה מחשב שלם, עם מערכת הפעלה שלמה משלה. היא כבדה ואיטית לעלות.
- קונטיינר הוא בסך הכול **תהליך רגיל** במערכת ההפעלה המארחת, שהליבה (kernel) של לינוקס מבודדת אותו:
  - **בעזרת namespaces** התהליך רואה רק את הקבצים, התהליכים והרשת שלו, ונדמה לו שהוא לבד במחשב.
  - **בעזרת cgroups** מגבילים כמה זיכרון ומעבד הוא יכול לצרוך.
- לכן קונטיינר עולה תוך שנייה ושוקל מעט: כל הקונטיינרים חולקים את אותה ליבה.
- **פרט חשוב למק**: אלה יכולות של הליבה של לינוקס. במק, Docker Desktop מריץ מכונה וירטואלית קטנה של לינוקס, והקונטיינרים רצים בתוכה.

### מה קורה כשמריצים `docker run hello-world`
- **לקוח ושרת**: הפקודה `docker` בטרמינל היא רק **לקוח**. היא שולחת בקשה ל־**daemon** – תהליך רקע שעושה את העבודה בפועל (במק הוא רץ בתוך המכונה הווירטואלית). זו ארכיטקטורת client-server קלאסית.
- **שכבות (layers)**: אימג' בנוי משכבות, וכל שכבה היא קבוצת שינויים במערכת הקבצים. השורה `58dee6a49ef1: Pull complete` היא הורדה של שכבה אחת. אם שני אימג'ים חולקים שכבה (למשל אותה מערכת הפעלה בסיסית), היא נשמרת פעם אחת בלבד.
- **ה־Digest** (`sha256:...`) הוא טביעת אצבע של תוכן האימג'. התג `latest` יכול להצביע מחר על גרסה אחרת, אבל ה־digest מזהה תמיד את אותו תוכן בדיוק.
- **אימג' רב־ארכיטקטורה**: ההודעה `(arm64v8)` אומרת שהורדה הגרסה למעבדי ARM, כמו במק עם שבב M. אותו שם אימג' מכיל גרסאות לכמה סוגי מעבדים, ו־Docker בוחר את המתאימה.
- **אחרי הריצה**: התהליך שבתוך הקונטיינר הדפיס הודעה והסתיים, ולכן הקונטיינר נעצר. הוא עדיין קיים, ואפשר לראות אותו עם `docker ps -a`.

### למה צריך אותו אצלנו
לא נכתוב `Dockerfile` בעצמנו. הכלי של Supabase משתמש ב־Docker כדי להריץ על המחשב שלך את כל רכיבי Supabase (מסד נתונים Postgres, שרת ההתחברות, שרת הזמן האמת ועוד), כל אחד בקונטיינר משלו. ככה יש לך עותק מלא של הסביבה, בחינם, בלי לגעת בענן.

### שאלות ראיון
- "מה ההבדל בין קונטיינר למכונה וירטואלית?" – ראה למעלה: ליבה משותפת מול מערכת הפעלה שלמה.
- "מה ההבדל בין image ל־container?" – תבנית מול מופע רץ.
- "מה קורה לנתונים כשקונטיינר נמחק?" – הם נמחקים איתו, אלא אם שמרת אותם ב־volume, שהוא אחסון שחי מחוץ לקונטיינר.
- "מה זה Docker Compose?" – קובץ שמגדיר כמה קונטיינרים שעובדים יחד ומרים את כולם בפקודה אחת. הכלי של Supabase עושה משהו דומה.

## Supabase

### מה זה
שירות שנותן לך את כל צד השרת "מוכן", מעל מסד הנתונים **Postgres**. לסוג השירות הזה קוראים Backend as a Service.
במקום לכתוב שרת בג'אווה עם Spring, שמחבר למסד נתונים ומטפל בהתחברות, מקבלים:
- **מסד נתונים Postgres** אמיתי. אפשר לכתוב SQL מלא.
- **ממשק API אוטומטי**: לכל טבלה נוצר API שאפשר לקרוא לו ישירות מהדפדפן.
- **שירות התחברות (Auth)**: גוגל, קישור קסם במייל וכו'. הוא מנפיק לכל משתמש מחובר **טוקן JWT** – מחרוזת חתומה שאומרת "זה המשתמש X".
- **שירות זמן אמת (Realtime)**: הדפדפן נרשם לשינויים בטבלה ומקבל עדכון ברגע שמישהו משנה שורה. ככה נועה תראה מיד בקבוק שהוספת.
- **אחסון קבצים (Storage)**: לתמונות התוויות.

### החלק הכי חשוב: Row Level Security
אם הדפדפן מדבר ישירות עם מסד הנתונים, מה מונע ממשתמש לקרוא את המרתף של מישהו אחר?
התשובה היא **RLS**: חוקים שכתובים בתוך Postgres עצמו, ברמת השורה. למשל: "מותר לקרוא שורה בטבלת הבקבוקים רק אם המשתמש שבטוקן חבר במרתף של הבקבוק".
מסד הנתונים בודק את החוק בכל שאילתה, לא משנה מאיפה היא הגיעה. גם אם מישהו עוקף את האתר ושולח בקשה ידנית, הוא יקבל רק את השורות שמותר לו.
זה הלב הטכני של הפרויקט שלך, ונקודה חזקה לראיון.

### שני המפתחות
- **מפתח ציבורי (anon / publishable)**: נמצא בדפדפן, וזה בסדר גמור. הוא רק מזהה את הפרויקט. ההגנה מגיעה מ־RLS.
- **מפתח שירות (service_role / secret)**: עוקף את כל חוקי ה־RLS. הוא נשאר רק בשרת, ולעולם לא בגיט ולא בדפדפן.

### חלופות שנדחו
- **שרת משלנו** (למשל Spring Boot): מלמד הרבה, אבל דורש לכתוב לבד התחברות, API וזמן אמת. זה ייקח חודשים לפני שיש מוצר.
- **הכלי Firebase** של גוגל: דומה, אבל מסד הנתונים שלו אינו טבלאי. המידע שלנו (מרתפים, מקררים, בקבוקים, הרשאות) מלא קשרים, ומסד טבלאי עם SQL מתאים לו יותר.

## Vercel

### מה זה
שירות אחסון (hosting) לאתרים, מאותה חברה שכתבה את Next.js.
מחברים אותו למאגר בגיטהאב, ומאותו רגע:
- כל `push` לענף הראשי → האתר נבנה ומתפרסם אוטומטית.
- כל Pull Request → מקבל **כתובת תצוגה מקדימה** משלו, כדי לבדוק שינוי לפני שממזגים אותו.

### איך הקוד רץ שם
אין "שרת" שרץ כל הזמן. הקוד שצריך לרוץ בשרת הופך ל**פונקציות serverless**: חתיכות קוד שמתעוררות כשמגיעה בקשה, רצות ונכבות. דפים סטטיים מוגשים מ־CDN, רשת שרתים בכל העולם שמגישה כל משתמש מהשרת הקרוב אליו.
**היתרון**: לא מנהלים שרת ומשלמים לפי שימוש (ובמקרה שלנו, בחינם).
**החיסרון**: "התנעה קרה" (cold start) – הבקשה הראשונה אחרי זמן שקט איטית יותר.

## משתני סביבה וקובץ .env

### הבעיה
הקוד צריך ערכים שמשתנים בין סביבות (הכתובת של Supabase על המחשב שלך שונה מזו שבענן), וגם סודות (מפתחות). אסור לכתוב אותם בקוד, כי הקוד נכנס לגיט, והגיט שלך ציבורי. בוטים סורקים את גיטהאב 24 שעות ביממה ומחפשים מפתחות שדלפו.

### הפתרון
**משתנה סביבה** הוא זוג של שם וערך שמערכת ההפעלה מעבירה לתוכנית כשהיא עולה. בג'אווה קוראים אותו עם `System.getenv("NAME")`, וב־Node עם `process.env.NAME`.
- **הקובץ `.env.local`**: מכיל את הערכים, שורה לכל משתנה (`NAME=value`). הכלי Next.js טוען אותו אוטומטית. הוא ב־`.gitignore`, ולכן לא נכנס לגיט.
- **הקובץ `.env.example`**: אותם שמות, בלי ערכים. הוא נכנס לגיט, כדי שמי שמוריד את הפרויקט ידע מה צריך להגדיר.
- **בענן**: מגדירים את אותם משתנים בממשק של Vercel.

### מלכודת שחשוב להכיר
בתוך Next.js, משתנה שהשם שלו מתחיל ב־`NEXT_PUBLIC_` **נכנס לקוד שנשלח לדפדפן**, וכל אחד יכול לראות אותו. לכן המפתח הציבורי של Supabase מקבל את הקידומת הזאת, ומפתח השירות לעולם לא.

### שאלות ראיון
- "מה תעשה אם דחפת מפתח לגיט בטעות?" – קודם כל **לבטל את המפתח ולהנפיק חדש**. מחיקת הקומיט לא מספיקה: ההיסטוריה כבר הועתקה, ויכול להיות שמישהו כבר סרק אותה.
